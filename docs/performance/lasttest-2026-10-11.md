# Last- und Performancetest

**Ziel:** Antwortzeiten und Stabilität unter realistischer und unter Überlast prüfen, Engpässe finden und beheben.

## Aufbau
- Datenbestand: Kopie eines vollständig migrierten Jira/Zephyr-Bestands (mehrere tausend Testfälle, Zehntausende
  Ausführungen mit Schrittergebnissen, Datenbank im niedrigen Gigabyte-Bereich). Getestet wird im größten Projekt
  (mehrere hundert Testfälle und Zyklen).
- Anemo als ein Node-Prozess auf einem Entwicklungsrechner (Apple Silicon), PostgreSQL 18 im Container,
  Verbindungspool 10.
- Werkzeug: [`tools/loadtest.ts`](../../tools/loadtest.ts), ohne Zusatzbibliotheken. Virtuelle Benutzer arbeiten mit
  folgender Gewichtung:
  - Testfälle suchen und öffnen (28 %), Ausführungen ansehen (24 %), Ergebnisse speichern (12 %);
  - Suche, Zyklenliste (16 %);
  - Matrix, Cockpit, Bericht, Duplikatanalyse (14 %).

```bash
# Testkopie anlegen und zweiten Server darauf starten (nie gegen Produktivdaten schreiben!)
docker compose exec -T db psql -U anemo -c "create database anemo_last"
docker compose exec -T db pg_dump -Fc -U anemo anemo | docker compose exec -T db pg_restore -U anemo -d anemo_last --no-owner
DATABASE_URL=postgres://anemo:anemo@localhost:5433/anemo_last ANEMO_PORT=8098 node server/src/main.ts &
# realistisch: 20 Benutzer mit Denkzeit 0,3–1,5 s
node tools/loadtest.ts --base http://localhost:8098 --db postgres://anemo:anemo@localhost:5433/anemo_last --project DEMO --users 20 --duration 60 --write
# Überlast: 50 Benutzer ohne Denkzeit
node tools/loadtest.ts … --users 50 --duration 30 --write --think 0-0
```

## Ergebnisse

**Realistisch (20 gleichzeitige Benutzer mit Denkzeit):** keine Fehler. Median 14 ms, 95 % unter 342 ms,
langsamste Anfrage 826 ms.

**Überlast (50 Benutzer ohne Pause; entspricht grob dem Mehrfachen echter Nutzung):**

| | vor der Optimierung | nach der Optimierung |
|---|---:|---:|
| Durchsatz | 102 Anfragen/s | **320 Anfragen/s** |
| Fehler | 0 | 0 |
| Median | 352 ms | **54 ms** |
| p95 | 1,51 s | **528 ms** |
| p99 | 2,92 s | **727 ms** |
| langsamste Anfrage | 12,2 s (Release-Cockpit) | **1,13 s** |

Nach der Optimierung, je Aktion unter Überlast:

| Aktion | p50 | p95 |
|---|---:|---:|
| Testfall öffnen | 14 ms | 391 ms |
| Ausführungen eines Zyklus | 23 ms | 437 ms |
| Ergebnis speichern | 35 ms | 372 ms |
| Testfallliste mit Suche | 39 ms | 401 ms |
| Release-Cockpit | 285 ms | 822 ms |
| Übergreifende Suche | 390 ms | 719 ms |

## Gefundene Engpässe und Maßnahmen
1. **Release-Cockpit und Testabschlussbericht** luden jeden Zyklus eines Plans einzeln: je Zyklus zwei Abfragen
   nacheinander, dazu ein erneuter Durchlauf über alle Ausführungen. Unter Last staute sich das am
   Verbindungspool auf bis zu 12 s. Jetzt genügt eine Abfrage, und die Ausführungen werden einmal gruppiert:
   ohne Last 40 % schneller, unter Last etwa 6-mal schneller.
2. **Duplikatanalyse** rechnet etwa 0,4 s auf dem einzigen Node-Thread und hielt in der Zeit alle anderen Anfragen
   auf. Das Ergebnis wird jetzt je Projekt zwischengespeichert, solange sich kein Testfall ändert.
3. Bereits zuvor behoben: Wiki-Parser linear (21-mal schneller über den gesamten Bestand), JUnit-Import linear.

## Einordnung und Empfehlungen
- Für den Regelbetrieb (Dutzende gleichzeitige Tester) reicht **ein** Anemo-Prozess mit Reserve. Echte
  Nutzung mit Denkzeiten erzeugt nur einen Bruchteil der Überlast-Anfragen.
- Rechenintensive Analysen laufen zwischengespeichert. Neue Analysen gehören ebenso in einen Zwischenspeicher
  oder in einen Worker-Thread.
- Die Datenbank ist der begrenzende Faktor unter Überlast. Für den Produktivbetrieb PostgreSQL mit
  ausreichend `shared_buffers` (≥ 25 % RAM) ausstatten. Der Pool von 10 Verbindungen genügt.
- Lasttest vor größeren Releases wiederholen (Werkzeug und Ablauf siehe oben).
